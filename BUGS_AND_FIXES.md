## [FIXED] Invite claim 500'd with a bare "Server error" — archived client's stale `supabaseUserId` collided with the unique index (2026-08-31, server)
**Symptom:** Immediately after fixing the unmounted-routers bug (previous entry), claiming an invite code on mobile returned a generic 500 "Server error" with nothing useful surfaced to the user.
**Root cause:** Two stacked issues. (1) `server/routes/appAuth.js`'s `claimHandler` had a bare `catch {}` with no logging at all — any exception was silently discarded, so the real cause was invisible. Adding logging revealed the actual error: `MongoServerError: E11000 duplicate key error ... index: supabaseUserId_1`. (2) The real cause: an old, archived test Client (`"Vhulenda Test Residence"`, created 2026-07-10 for earlier SecureWatch testing) still had `supabaseUserId` set to the same identity now trying to claim a fresh invite. `middleware/clientAuth.js:55` filters `archived: false` when resolving the logged-in client, so the archived record is invisible to normal login (correctly reports "No linked client account") — but the MongoDB unique index on `supabaseUserId` has no such filter, so it still blocks re-claiming with that identity. Archiving a client never cleared `supabaseUserId`/`appInviteCode`/`appInviteExpiresAt`, so this wasn't unique to test data — the same collision could hit a real client later (archived, then re-issued an invite, or their identity reused some other way). The identical gap existed on `Technician`/`ResponseOfficer` deactivation too — same schema (`supabaseUserId` sparse-unique), same soft-delete-never-clears-the-link pattern.
**Fix:** Added proper error logging to the `claimHandler` catch (`console.error('[appAuth] claim failed:', err)`, kept permanently — a bare swallow-all catch on a write path is a defect on its own). For the immediate block (same session, 2026-08-31): confirmed with the user this was their own test data, then (per their choice) unarchived the test Client directly in MongoDB Atlas (`archived: false`) rather than clearing the identity link, since it was already correctly linked. **Systemic fix (2026-09-01 follow-up session)**: `Client`'s archive handler (`server/routes/clients.js`, `DELETE /:id`, now `archiveHandler`) and `Technician`/`ResponseOfficer`'s deactivate handlers (`server/routes/technicians.js`, `server/routes/responseOfficers.js`, `DELETE /:id`, now `deactivateHandler`) all now `$unset` (not `$set: null` — the index is sparse, so a stored literal `null` is still indexed and would just move the collision to the next archive/deactivate) `supabaseUserId`/`appInviteCode`/`appInviteExpiresAt` on archive/deactivate.
**Tests:** Live-verified at the time (after unarchiving, `/api/app/me` resolved correctly on the real device, user confirmed live footage plays end-to-end — "Great it works"). Systemic fix: 9 new unit tests across `clientsCreateUpdate.test.js`, `technicians.test.js`, `responseOfficers.test.js` (asserts the `$unset` shape on each `findByIdAndUpdate` call, 404 case, and error case for each of the three handlers). Full suite 537/537.

## [NOTE, not a bug] Vendor player SDK's screenshot Blob is mislabeled — filename says `.jpg`/`image/jpg`, actual bytes are PNG (2026-08-04, admin + mobile)
**Symptom:** While verifying the new live-view screenshot feature, a real screenshot downloaded from the admin app (`live-<id>-<timestamp>.jpg`) was inspected with `file` and reported `PNG image data, 704 x 576, ... non-interlaced` — not a JPEG, despite the filename and the vendored SDK's own `Blob` MIME type both declaring `image/jpg`.
**Root cause:** Not our code — this is the vendored Dahua player SDK's own internal behavior (`admin/src/lib/dahuaPlayer/playerWasm/PlaySDKInterface.js`): the canvas-capture path calls `canvas.toDataURL()` (which defaults to PNG encoding) and then wraps the resulting bytes in a `Blob` hardcoded to `{type: 'image/jpg'}`, regardless of what was actually encoded. The mismatch is entirely inside the vendor's minified SDK; there's nothing in our wrapper code to change without patching a vendored, byte-identical-across-two-copies file.
**Impact:** None functionally — the downloaded file opens correctly in any real image viewer or OS photo app, since those sniff actual file content rather than trusting the extension. Documented here only so a future feature that does anything content-type-strict with saved screenshots (e.g. re-uploading them somewhere with server-side validation) doesn't get tripped up assuming the bytes match the `.jpg` name.
**Fix:** None applied — not a defect worth patching a vendored file for. No tests added.

## [FIXED] Mobile player page's SDK requests all 500'd — CORS middleware ran ahead of static asset serving (2026-08-04, server)
**Symptom:** Building the new server-hosted `/player/` page (the Dahua plugin-free web player, loaded by the mobile app's WebView) for real streaming live view — verified live via a headless-Chromium script hitting the page directly. The player's `videoPlay-js.js` module and its WASM sub-resources intermittently, then consistently, 500'd with no application-level error logged. Curling the same URL plainly succeeded every time; only requests carrying an `Origin` header failed.
**Root cause:** `<script type="module">`/ES module `import` fetches always run in CORS mode and attach an `Origin` header, even for same-origin requests. The new static-file mount (`app.use(express.static(...))`, serving `/player/`, `/videoPlayer/`, `/WasmLib/`) was placed after the existing global `cors()` middleware in `server/index.js`. That CORS middleware's allowlist only contains the client/admin dev origins (`CLIENT_ORIGIN`/`ADMIN_ORIGIN`) — the server's own origin (`http://localhost:3001`) was never in it, since nothing had ever needed to request the server's own resources with an `Origin` header before. Every module-script fetch got rejected by the `cors` package's `origin` callback, which Express's default error handler turns into an opaque 500 — masking the real "Not allowed by CORS" cause entirely.
**Fix:** Moved `express.static(path.join(__dirname, 'public'))` to before `app.use(cors(...))` in `server/index.js`, so static assets bypass the CORS gate entirely rather than trying to add the server's own origin to the allowlist. This is correct, not a workaround: these are public, non-sensitive SDK files (JS/WASM) meant to be loadable from anywhere a WebView or browser points at them — no cookies or auth ride on them, unlike the `/api/*` routes the CORS check still protects. Confirmed the `/api/*` CORS behavior is unaffected: `curl` with `Origin: http://localhost:5175` against `/api/clients` still returns the correct `Access-Control-Allow-Origin` header after the reorder.
**Tests:** No unit test (this is Express middleware ordering, not app logic — not meaningfully unit-testable without spinning up the real HTTP server). Verified live: before the fix, a headless-Chromium request to `/videoPlayer/videoPlay-js.js` with an `Origin` header returned 500; after moving the static mount, the same request returns 200, and the full player page loaded a real stream end-to-end (`ready` → `playing`, screenshot showed genuine moving video with an advancing NVR timestamp overlay). Full server suite 528/528 both before and after (this bug wasn't caught by any existing test, since none exercise the real Express app with CORS headers set).

## [FIXED] Live view failed on both web and app — snapshot-readiness retry budget was ~7x too small, and mobile had no retry at all (2026-08-04, server)
**Symptom:** User reported live view of cameras not working from either the admin web UI or the mobile app (the standing "re-verify live" item from the 2026-08-03 entry below). Reproduced and measured live against the real NVR (`BD10A23PAJF6096`): `setDeviceSnapEnhanced` returned `status: ready` with an OSS URL, but fetching that URL immediately gave HTTP 404 — the image only became fetchable **3.6–5.7 seconds later** (measured across 3 online channels).
**Root cause:** The 2026-08-03 entry's "root cause 3" fix (retry the OSS fetch) was real but **undersized**: `fetchSnapshotWithRetry` in `server/routes/cameras.js` allowed 3 attempts × 400ms ≈ 0.8s total, while the real capture→upload latency is 3.6–5.7s — so the admin proxy nearly always exhausted its retries and 502'd. Worse, the mobile path never got any retry at all: `appCameras.js`'s `/stream` route hands the raw OSS URL straight to the app, whose `Image.prefetch()` fetches it instantly, hits the 404 race full-on, and surfaces "Received a snapshot but the image failed to load" on effectively every poll tick. Two surfaces, one shared root cause: nothing verified the URL was actually fetchable before reporting it ready.
**Fix:** Moved the readiness wait into the shared layer — `server/services/dahua.js`'s `getSnapshotUrl` now polls the OSS URL (1-byte `Range: bytes=0-0` GET — cheap, and OSS pre-signed URLs sign the HTTP verb so HEAD is rejected) every 700ms up to a 10s budget (comfortably above the 5.7s worst measured case) and only returns `status: 'ready'` once the object actually exists; if it never lands (e.g. an offline channel that will never upload), the caller gets the honest `unavailable` 503 instead of a dead URL. Since both the admin `/live`+`/live/image` routes and mobile's `/stream` route consume `getSnapshotUrl`, this fixes web and app at once — **zero frontend changes needed**. `cameras.js`'s existing small `fetchSnapshotWithRetry` cushion was left in place (harmless defense in depth; its first attempt now succeeds).
**Tests:** 4 new cases in `server/__tests__/dahua.test.js`: Range-GET probe shape (never HEAD), 404-then-ready race survival, unavailable-after-budget-exhausted (fake timers), transient-network-error-keeps-polling; plus `fetch` never called when the Dahua API itself fails. Full suite **510/510**. **Verified live against the real NVR:** `getLiveViewSession` on channel 1 returned `ready` after 4.3s and an *immediate* fetch of the returned URL gave HTTP 200 with a complete 239KB JPEG (pre-fix, the same immediate fetch 404'd). Note: the fix is server-side only — production (Railway) needs a deploy to pick it up.

## [FIXED, pending hands-on re-verification] Live View snapshot showed a permanently broken image (2026-08-03, server + admin + mobile)
**Symptom:** User opened the new "View Live" modal (`ClientDetail.jsx`) against a real imported channel on the real NVR (`BD10A23PAJF6096`) — the modal correctly showed `hasLiveView:true, available:true` with a real Dahua/Aliyun OSS URL, but the `<img>` rendered as a broken-image icon instead of the photo. Two distinct, real bugs were found in sequence — the first fix wasn't sufficient on its own; the second was the actual blocker.
**Root cause 1 (contributing, fixed first):** Fetching a fresh Dahua snapshot (`setDeviceSnapEnhanced`) is a real multi-hop round trip — our server → Dahua's Frankfurt API → the physical NVR → an Aliyun OSS upload → back to us — that can take a few seconds. The original polling design swapped the `<img>`'s `src` the instant each new JSON response arrived, without waiting for the previous (or even the current) image to finish downloading — aborting an in-flight download every 5s tick.
**Root cause 2 (the actual blocker, found after fixing #1 didn't resolve it):** Curling the exact URL the browser received returned a genuine, complete 238KB JPEG every time (ruled out URL expiry, OSS referrer whitelisting, and CSP as causes by testing each directly) — so a `new Image()` preload (root cause 1's fix) still failed with `onerror`. Dumping the real response headers (`curl -D -`) showed why: the Aliyun OSS object's `Content-Type` is `application/octet-stream`, not `image/jpeg` — Dahua's own upload pipeline doesn't set it correctly, even though the bytes are a genuine, complete JPEG (confirmed via `file`). Pasting the URL directly into a browser tab downloaded it as a generic file instead of displaying it — consistent with the wrong Content-Type, and the same header is why a plain `<img>`/`Image()` load also refuses to render it. This is a Dahua/Aliyun-side issue, not something fixable by changing the URL or request.
**Fix:** Two parts, both needed:
1. `admin/src/pages/ClientDetail.jsx`'s `fetchLiveView` (root cause 1) preloads the next frame in the background first and only swaps the visible image once it's confirmed fully loaded — the previous frame stays on screen in the meantime. The mobile equivalent (`mobile/src/hooks/useCameraStream.js`) had the identical latent bug (same 5s-poll, same round trip) even though it hadn't been exercised yet — fixed proactively using `Image.prefetch()`.
2. New server route `GET /api/cameras/:id/live/image` (`server/routes/cameras.js`'s `liveViewImageHandler`) — proxies the actual snapshot bytes server-side (fetches the Dahua/OSS URL itself, via `node-fetch`) and re-serves them with an explicit `Content-Type: image/jpeg`, sidestepping whatever header Dahua's storage sends. `ClientDetail.jsx` now points at this proxy instead of the raw Dahua URL, fetching it as a blob and rendering via `URL.createObjectURL` (with `URL.revokeObjectURL` cleanup on each swap and on modal close/unmount, to avoid a memory leak from a new blob URL every poll tick). Mobile is unaffected by this second issue for now — `Image.prefetch()`'s failure mode wasn't confirmed broken by the same Content-Type problem (RN's native image decoders are typically more lenient than Chromium here), so no proxy was added mobile-side without evidence it's needed; flagged as something to watch when mobile is actually tested.
**Root cause 3 (found immediately after deploying the proxy fix):** server logs from the real proxy showed `snapshot image fetch failed: 404` on repeat — the OSS object doesn't exist yet at the instant Dahua's API hands back its URL. Dahua's snapshot API returns the URL immediately while the actual upload to that path happens asynchronously on their end; fetching it the instant it's returned can beat the upload. This is why curl succeeded consistently earlier — by the time those manual tests ran, a few seconds had already passed. **Fix:** `liveViewImageHandler` now retries the OSS fetch up to 3 times with a 400ms backoff between attempts (`fetchSnapshotWithRetry`) before giving up with a 502 — covers the race without blindly delaying every request by a fixed amount.
**Tests:** New `server/__tests__/cameraLiveView.test.js` cases for `liveViewImageHandler` (404/503 passthrough from the not_configured/unavailable states, 502 after retries are exhausted on a persistent OSS failure or a hard throw, and confirms the response is sent with an explicit `image/jpeg` Content-Type regardless of the mocked upstream). No automated test for the front-end image-swap timing itself or the OSS upload race specifically (real-network-timing behavior, not meaningfully mockable). Full server suite 506/506, `admin/npm run build` clean. **Still owed:** the user re-verifying live against the real NVR that the image now actually renders and keeps refreshing without going broken.

## [FIXED] Newly-imported NVR channels always showed "Offline" until manually corrected (2026-08-03, server)
**Symptom:** User noticed real imported channels (e.g. "BACK OFFICE WEST" on the real bound NVR `BD10A23PAJF6096`) showed status "Offline" in the admin UI right after import, even though the device and channel were actually online — required manual correction, which shouldn't be necessary since camera health is meant to come from Dahua/P2P, not admin input.

Full suite 490/490. Verified live: the 3 real channels already affected by the pre-fix bug (created before this fix landed) were corrected via `PATCH /cameras/:id/status` against Dahua's live-confirmed status (all 22 channels on the real NVR are online) — a one-off data correction; all future imports get the right status automatically with no manual step.

## [FIXED] Dahua callback would have silently corrupted every real event's id/companyId (2026-08-01, server)
**Symptom:** Caught during hands-on live-server verification of the new Dahua Open ARC callback route (`server/routes/dahuaCallback.js`, this session). A `bindDevice` test event sent with the real `DAHUA_ARC_COMPANY_ID` (a 19-digit integer) was rejected by the route's own companyId defense-in-depth check as "not addressed to our company" — even though the value sent was byte-for-byte the same one configured in `.env`.
**Root cause:** Every Dahua Open ARC event's `id` (message id) and `companyId` are 19-digit integers in the documented examples — larger than `Number.MAX_SAFE_INTEGER` (2^53). `express.json()`'s default body parser calls `JSON.parse`, which silently rounds numbers past that range to the nearest representable double (confirmed live: `1685825282387133305` becomes `1685825282387133200` after parsing — a different number, no error thrown). This corrupted **two** load-bearing fields at once: the companyId check would reject every real event (as observed), and — more seriously, since it wouldn't have thrown any visible error — the corrupted `id` would have been used as the idempotency key (`DahuaEventLog.dahuaMessageId`) and the value sent back to Dahua's `messageAck` endpoint, meaning Dahua would never see the real message acknowledged and would keep re-pushing it indefinitely, while our dedupe logic keyed off a value Dahua's system doesn't recognize.
**Fix:** `server/index.js`'s global `express.json()` now takes a `verify` callback that stashes the pre-parse raw body Buffer on `req.rawBody`. `server/routes/dahuaCallback.js` added `extractExactIntField()`, which regexes the exact digit string for `id`/`companyId` straight off the raw bytes, bypassing `JSON.parse`'s number handling entirely for those two fields (falls back to the parsed value only if no raw body was captured, e.g. in unit tests that construct `req` by hand). All other fields (`msgType`, `deviceId`, `channelId`, etc.) are small enough or non-numeric, so the normal parsed body is fine for them.
**Tests:** `server/__tests__/dahuaCallback.test.js` — two new tests reproduce the exact live bug (a companyId that changes value when run through `JSON.parse`) and confirm the fix extracts the untouched value; a third documents the fallback behavior when no `rawBody` is present. Verified live against the real dev server + real MongoDB Atlas + real Dahua Frankfurt API with the real `DAHUA_ARC_COMPANY_ID`: the same event that was wrongly rejected before the fix was accepted after it, and the stored `DahuaPendingBind.companyId` matched the real value exactly (not the JSON.parse-rounded one). Full server suite 471/471.

## [FIXED, pending hands-on print verification] Printed quotes showed blank/"-" totals — customer-facing PDF was wrong (2026-07-17, admin)
**Symptom:** Found during a bug audit of the freshly-overhauled admin quote builder (`QuoteBuilder.jsx`/`QuotePrint.jsx`, both uncommitted). Two separate paths produced a printed quotation whose numbers were blank even though the *saved* quote record was correct:
1. **Manual/sectioned mode:** every line item's **Total** column rendered as `-`. The bottom totals box (Subtotal/VAT/Grand Total) was correct, but each line showed no total.
2. **Auto-priced mode:** the entire printout (line rows *and* Total/VAT/Grand Total) rendered blank/`-` whenever the user clicked **Send Quote** without first clicking **Calculate**, or when reprinting a quote that had just been reopened from the client file.
**Root cause:**
1. `QuotePrint`'s manual branch read `item.lineTotal` for each row, but the `sections` state handed to it from `QuoteBuilder` is the *live editor state* — its line items only carry `qty`/`unitPrice`/`discountPct`, never a computed `lineTotal` (that field only exists on the server-persisted copy, which the print never receives). So `fmt(undefined)` → `-` on every line.
2. `QuotePrint`'s auto branch renders from the client-side `breakdown` object (the excl-VAT decomposition returned by `POST /api/quotes/calculate`). `breakdown` is only populated by the Calculate button and is **never set by `loadQuote()`** — so on send-without-calculate or on a reopened quote, `breakdown` was `null`, making `grand` `undefined` and every line row empty. (Rendering the auto printout from the saved quote's stored `items[]` instead is not viable: those store VAT-*inclusive* unit prices/line totals, whereas the print's Total column is excl-VAT with VAT added at the bottom — using them would double-count VAT.)
**Fix:** `admin/src/components/QuotePrint.jsx` — manual rows now use `item.lineTotal != null ? item.lineTotal : calcLineTotal(item)`, reusing the already-unit-tested `calcLineTotal` from `admin/src/utils/quoteCalc.js` so a live-state line still prints a correct total. `admin/src/pages/QuoteBuilder.jsx` — extracted the calculate API call into a shared `fetchBreakdown()`; `save()` now refreshes the breakdown from the server for auto-mode quotes right before opening the print dialog (on send), so the printed PDF always reflects current inputs instead of a stale or missing breakdown. If that refresh fails, the quote is still saved and the admin gets a visible message to Calculate and print again (never a silent blank PDF).
**Tests:** `admin/` has no JS test harness (long-standing, documented gap). Verified `calcLineTotal` produces correct totals on the exact live section-item shape (string `qty`/`unitPrice`/`discountPct`) via a Node check (`2 × R100 @10% → R180`, empty line → `R0`), and `admin/ npm run build` is clean. Hands-on browser check of the rendered printout (manual line totals populate; auto send-without-calculate and reopened-quote reprint both show correct numbers) is still owed — no browser-driving tool in this environment, per the standing note in HANDOFF.md.

## [FIXED] React warning "Cannot update a component (JobDetailScreen) while rendering a different component (SignaturePad)" (2026-07-13, mobile)
**Symptom:** User-reported while hands-on testing the technician Sign-off step in Expo Go. Console showed the React warning naming `JobDetailScreen` and `SignaturePad`.
**Root cause:** `SignaturePad`'s `emit()` called the `onChange` prop — which `JobDetailScreen` passes as `setSignatureStrokes` directly — synchronously from inside its `PanResponder`'s `onPanResponderRelease` gesture callback (and from `clear()`). Under this project's stack (RN 0.81 / React 19, New Architecture), a parent's state setter called synchronously from a child's native gesture callback can still be perceived by React as happening "during" a render pass elsewhere in the tree, triggering this warning. Calling an ancestor's setter directly from a descendant's event handler this way is the wrong pattern regardless of the precise trigger — the correct pattern is to notify the parent from an effect, strictly after the child's own state commits.
**Fix:** `mobile/src/ui/SignaturePad.js` — removed the `emit` callback entirely; added a `useEffect(() => { onChange && onChange(strokes) }, [strokes, onChange])` that notifies the parent whenever `strokes` changes, instead of calling `onChange` inline inside `onPanResponderRelease`/`clear`.

## [FIXED, pending on-device confirmation] Sign-in spins forever, never reaches the app (2026-07-10, mobile + server)
**Symptom:** Tapping "Sign in" in the SecureWatch mobile app showed a permanent loading spinner — never errored, never navigated into the app.
**Root cause:** Two layered issues. (1) `server/middleware/clientAuth.js` verified Supabase-issued JWTs with `jwt.verify(token, SUPABASE_JWT_SECRET)` — a shared-secret HS256 check. This Supabase project signs tokens asymmetrically (RS256/ES256) via its newer JWT signing-keys system, so verification failed on every request with `invalid algorithm`, confirmed via temporary diagnostic logging (per the "log before guessing" rule) — no secret value, legacy or otherwise, could have fixed this. (2) That failure was invisible in the UI because `mobile/src/screens/auth/SignInScreen.js`'s `submit()` only resets its `busy` flag inside the `catch` block; when `signIn()` itself succeeds (Supabase auth passes) but the follow-up `/api/app/me` call then 401s, `AuthContext` sets status back to `'signedOut'` — the same value it already had — so React never re-renders/navigates and the spinner is left frozen with zero feedback.
**Fix:** Rewrote `server/middleware/clientAuth.js` to verify tokens against Supabase's published JWKS (`jwks-rsa`, fetched from `${SUPABASE_URL}/auth/v1/.well-known/jwks.json`, cached, algorithms `['RS256','ES256']`) instead of a shared secret — works for both legacy and current Supabase signing configurations. Removed the now-unused `SUPABASE_JWT_SECRET` from `server/.env.example` (real `.env` value left in place but is no longer read). Added `console.error` logging on verification failure (kept permanently — this path was previously silent). The `SignInScreen` frozen-spinner UI bug is still open — same-status re-render gap should be fixed separately so any future 401 (not just this one) surfaces visibly instead of hanging.
**Tests:** Added `server/__tests__/clientAuth.test.js` (10 cases: missing/malformed/no-kid/wrong-signature/expired tokens, JWKS lookup failure, unlinked client, DB error, valid RS256 token, valid ES256 token) — all pass. Full server suite: 71/71 pass. Not yet re-verified on-device end-to-end — next sign-in attempt should confirm the app actually reaches the main tab navigator.

## [FIXED] `AuthContext` `onAuthStateChange` deadlock risk (prior session, mobile)
**Symptom:** Potential deadlock in supabase-js when signing in.
**Root cause:** `AuthContext`'s `onAuthStateChange` handler called `resolveProfile()` (which itself awaits further Supabase calls) synchronously inside the `onAuthStateChange` callback. Supabase's own docs warn this can deadlock supabase-js, since the callback is expected to return quickly.
**Fix:** Deferred the call with `setTimeout(resolveProfile, 0)` in `mobile/src/state/AuthContext.js`, so it runs after the `onAuthStateChange` callback has returned.
**Tests:** No automated test for this timing-sensitive path yet; verified manually that sign-in resolves to the correct auth status without hanging.
