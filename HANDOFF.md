## Session 2026-07-11: shake-to-SOS feature brainstorm (planning only, no code)

User wants a feature where shaking the phone triggers a panic/SOS alert, as an alternate trigger alongside the existing hold-to-arm PANIC button (`mobile/src/screens/HomeScreen.js` + the panic API — `POST /api/app/panic` etc., all already built). Rationale: hold-to-arm needs fine motor control; a real panic situation often takes that away first, and a gross-motor shake gesture is more usable one-handed/trembling/without looking at the screen.

**Design direction settled in discussion (not yet built, not yet written into `features.md`):**
- Shake **arms a countdown**, it does not fire instantly — full-screen 5–10s countdown with a big Cancel + haptic pulses, THEN dispatches if not cancelled. This is the false-alarm mitigation: a phone bouncing in a pocket/bag must not silently dispatch armed response.
- Detection should require a deliberate gesture (multiple direction reversals above a real g-force threshold in a short window), not a single bump.
- Add `source: 'shake' | 'button'` to the panic alert payload — cheap to add now, gives free false-alarm triage data later.
- Opt-in toggle in the app (default **off** at launch), plus a **practice/test mode** that runs the full countdown UI without actually dispatching, so users can learn/trust the gesture without spamming the dispatcher.
- Proposed implementation shape: `mobile/src/lib/shakeDetector.js` as a **pure function** (samples in → shake-detected boolean out), fully unit-testable with synthetic fixtures — flagged as the likely first real justification for setting up the mobile test harness (jest-expo), a gap noted in earlier sessions. A `useShakeToSos()` hook wires it to `expo-sensors` Accelerometer only while the toggle is on and app state is active; an `SosCountdown` overlay reuses the existing `triggerPanic()` from `RealtimeContext`.

**Background/screen-off limitations — discussed at length, important to not re-litigate without new info:**
- **True background shake detection (app closed/backgrounded, screen off) is not realistically achievable on iOS at all** — Apple does not grant third-party apps continuous background accelerometer access; that class of trigger is reserved for Apple's own Emergency SOS (side-button 5×), which third-party apps cannot hook into.
- **Android can technically do it via a foreground service**, but it requires a standalone build (not testable in the current Expo Go workflow), costs real battery, and is fragile in practice — Samsung/Huawei/Xiaomi-class OEM battery managers frequently kill background services regardless of what the app requests, which is a real problem in the SA market specifically. Parked, not recommended to build until standalone builds exist and even then should be positioned as best-effort, never guaranteed.
- Explored "screen-locked, one tap" alternatives to background shake:
  - **Lock Screen widget is NOT a true zero-unlock trigger on iOS** — WidgetKit lock-screen widgets are tap-to-launch only; tapping requires Face ID/passcode before the app opens and can act. Fast, but not literally unlock-free.
  - **On Android, the true zero-unlock mechanism is a persistent/ongoing notification with a tappable action button** — not a widget. Modern Android removed lock-screen widgets (~Android 5+) and home-screen widgets require unlocking like iOS now does; an ongoing notification's action button is what actually fires without unlocking.

## Session 2026-07-10: Dahua hardware-integration research, feature brainstorm, DEPP partner registration (planning only, no code)

### 1. Dahua API capability audit → tiered by who it's for
Went through the full capability list from the user's research (media retrieval/playback, PTZ/relay/device control, smart events/push, device management) and split it:
- **Client-facing, build first:** live view, snapshot, recorded playback, motion/intrusion push notifications, hardware diagnostics (SD card errors, video loss, tamper) feeding into `aiChat.js`'s existing camera-status prompt (today that prompt only has the manually-set `status`/`signal` enum on `Camera` — real diagnostics would make the AI's troubleshooting actually accurate instead of working off admin-entered data).
- **Client-facing, phase 2 (more complexity/risk):** two-way audio, PTZ (only matters if any installed cameras are actually motorized — worth checking the real install base), relay/gate output (powerful but liability-sensitive — leaned toward *not* client self-service on day one, needs explicit confirm-style UX if built).
- **Admin/technician-only, never client-facing:** remote reboot, firmware push, device password/account management. Real capabilities of the API, but exposing "reboot the client's NVR" as a self-service button is a support/liability risk — this belongs on the ops side, not in the client app.

### 2. Facial recognition & ANPR (number plate recognition)
Both ride on Dahua's on-device IVS/WizSense metadata (the camera does detection/OCR locally, API just hands you structured events) — this is a UI/notification/allowlist-management build, not a from-scratch ML pipeline.
- **ANPR — lower risk, prioritize:** known-vehicle allowlist per client (silent log, no alert for the household's own cars), unknown-plate → push notification with snapshot, searchable plate log, and a natural pairing with the gate-relay feature (allowlisted plate auto-opens the gate).
- **Face *detection* only** (person-vs-motion, no identity) — safe, same as what Ring/Arlo ship, cuts false alerts from trees/animals/shadows. Build without hesitation.
- **Face *identity matching* ("familiar face" vs unknown, repeat-visitor tracking) — flagged, not decided.** POPIA classifies biometric data used for identification as *special personal information* with stricter consent requirements than ordinary CCTV footage, and the subjects being biometrically processed here are every visitor/delivery driver/passerby the camera catches, not just the client. Since the admin dashboard already has a Compliance workflow, this is a domain the business clearly takes seriously — **treat "should we build identity-matching facial recognition, and under what consent model" as an explicit business/legal decision to make before scoping it**, not something to default into just because the hardware supports it.

### 3. Competitive landscape (SA market) → validated the app's existing architecture
User's research split the local market into three tiers (hardware-native apps like DMSS/Hik-Connect, national armed-response apps like ADT/Chubb, on-demand panic apps like Namola) — none of which combine panic dispatch + live chat + camera status + admin response in one system the way SecureWatch already does. The "unified command center" positioning isn't aspirational, it matches what's already built.
- **Highest-leverage, nearly-free feature identified: load-shedding-aware offline alerts.** `Camera.status` (`server/models/Camera.js:9`, online/offline enum) already exists — nothing currently pushes when it *transitions*, it's only read on-demand by the dashboard/chat. Wiring "camera went offline → immediate push notification" needs no Dahua SDK/P2P access at all and is the single most locally-specific, hard-to-copy feature on the list. **Recommended as the first thing to build, independent of the DEPP/SDK timeline.**
- Adaptive bitrate streaming (Dahua main/sub stream switching, `subtype=0`/`subtype=1`) is a **design constraint to bake into live-streaming from day one**, not a bolt-on — retrofitting it after building "dumb" full-bitrate streaming would be materially more painful.
- Filtered AI alerts (human/vehicle only, night-hours only) is a config layer on top of the same IVS metadata pipeline as the plate/person-detection work above, not a separate track.
- One-tap gate/relay button belongs directly on the live-view screen itself (not buried in a menu) — the reasoning from the research (don't make someone menu-hunt during a hijacking window entering their property) is a real UX constraint worth keeping if/when relay control gets built.
- Two-way audio "virtual guarding" (push notification → live view → speak to warn off a trespasser) was originally filed as phase-2-for-complexity but is arguably a bigger differentiator than first ranked, since none of the three competitor tiers offer it at all — worth reconsidering its priority when sequencing.

### 4. Reachability question — resolved: use Dahua's P2P/cloud relay, not port-forwarding or a homegrown relay
Direct question from the user: "if the homeowner is on cellular at work, not home WiFi, can they still see the feed and do everything else?"
- **Notifications are location-independent already** — device → cloud → phone push, doesn't matter where the phone is. This is part of why the offline-alert feature above is the right thing to build first.
- **Live view / playback / snapshot / PTZ / relay all need real reachability solved.** A Dahua device on a client's home LAN has a private IP, not reachable from cellular. Three options were weighed:
  1. **Dahua's own P2P/cloud relay (chosen approach).** Built into every device (Settings → Network → P2P, tied to device serial), it's what Dahua's own DMSS app already uses — no router config needed client-side. Requires Dahua SDK/Open API access (the DEPP registration, see below) to integrate into a *custom* app rather than DMSS.
  2. **Port forwarding + DDNS — ruled out.** Exposes devices directly to the internet (scanner/botnet target — see security section below), most SA ISPs (especially LTE/fixed-wireless) use CGNAT so many clients wouldn't even have a forwardable public IP, and requires router config no homeowner will do.
  3. **Roll-your-own relay server — deprioritized.** Would work (same pattern Ring/Arlo/Nest use) but Dahua's P2P already provides this for free; building/hosting your own would likely be reinventing what option 1 already gives you.
- **No new hardware/servers needed at residential sites.** Every existing residential package already includes an NVR (per CLAUDE.md's business rules table) — that already-installed device is the "server." P2P is a free config toggle on it, using whatever internet connection the house already needs for the cameras/app to work at all.

### 5. Security research (CVE audit) → produced a defense plan for the eventual integration
User brought a second research doc on Dahua's CVE history (unauthenticated RCE via ONVIF/RPC handlers, the 2017 "Dahua backdoor" credential leak, DoS crash bugs, privilege escalation). Spot-checked the two headline CVEs (CVE-2025-31700/31701, ONVIF + RPC file-upload buffer overflows, CVSS 8.1) via web search — **confirmed real and disclosed/patched**, and critically, search results explicitly note they're "particularly impactful on devices that are internet-facing via port-forwarding or UPnP" — independent validation that the P2P-not-port-forwarding decision above is correct for security reasons, not just usability. Could not personally verify every CVE number in the user's list, but the overall threat pattern (Dahua-class IoT cameras as a heavily-targeted, historically backdoor-prone device class) is well-documented regardless.

**8-point defense plan, to lock in architecturally before/while building the SDK integration:**
1. Never port-forward — already the plan (P2P relay instead); confirmed as the actual defense against the exploited CVE class, not just a convenience choice.
2. **Firmware update discipline — the real gap, not yet solved.** Every cited vulnerability was eventually fixed by a firmware update; an un-updated camera stays exploitable regardless of network exposure. Needs a real process: track firmware version per installed device, flag out-of-date ones. Natural home: extend `admin/src/pages/Maintenance.jsx` with a per-client/per-camera firmware-version field and a "needs update" flag, so this becomes a recurring tracked task instead of an install-time-only concern.
3. **Unique strong admin credentials per install, never shared/reused across clients** — stored encrypted server-side (not on the client's phone), since the backend will need them to make SDK calls on the client's behalf anyway.
4. **Server-mediated device access — client app never talks to the camera directly.** Client app authenticates to Mashtronics' own backend (already the pattern — Supabase bearer → API); the server, holding real device credentials, makes the SDK/P2P calls. Keeps device creds off the client's phone, allows central credential rotation without an app update, and gives a server-side audit log for sensitive actions (e.g. "who triggered the gate relay and when").
5. Recommend a segmented/isolated network (VLAN) for cameras at install time — technician/install-checklist item, limits blast radius if a device is ever compromised.
6. **Reframe the offline-alert feature (section 3 above) as a security control, not just UX** — one of the cited DoS-style vulnerabilities describes attackers deliberately crashing a camera to blind it right before a physical break-in; the same alert that solves the load-shedding UX problem is also the detection mechanism for that attack pattern.
7. Keep the client-facing API surface narrow — reinforces the admin-only tier from section 1 (reboot/firmware/credentials never client-facing); smaller blast radius if a client account/phone is ever compromised.
8. Watch Dahua's own PSIRT/security-advisory feed (`dahuasecurity.com/about-dahua/trust-center/dahua-psirt`) so new CVEs affecting installed models are caught proactively, not discovered after an incident.

## This session: two auth bugs fixed, one large feature built

### 1. Fixed — sign-in spun forever, never reached the app
**Root cause (two layered issues):**
1. `server/middleware/clientAuth.js` verified Supabase JWTs with `jwt.verify(token, SUPABASE_JWT_SECRET)` — a shared-secret HS256 check. This Supabase project signs tokens **asymmetrically** (RS256/ES256) via its newer JWT signing-keys system, so every verification failed with `invalid algorithm`. No secret value — legacy or otherwise — could have fixed this.
2. That failure was invisible in the UI because `mobile/src/screens/auth/SignInScreen.js`'s `submit()` only resets its `busy` flag inside the `catch` block. When `signIn()` succeeds (Supabase auth passes) but the follow-up `/api/app/me` call then 401s, `AuthContext` sets status back to `'signedOut'` — the *same* value it already had — so React never re-renders/navigates and the spinner is left frozen with zero feedback. **This UI bug is still open** — worth fixing separately so any future 401 surfaces visibly instead of hanging. Not yet done.

**Fix:** Rewrote `server/middleware/clientAuth.js` to verify tokens against Supabase's published JWKS (`jwks-rsa`, fetched from `${SUPABASE_URL}/auth/v1/.well-known/jwks.json`, cached, algorithms `['RS256','ES256']`) instead of a shared secret. Exported `verifySupabaseToken` from that file so there's exactly one JWT-verification implementation. Removed the now-dead `SUPABASE_JWT_SECRET` from `server/.env.example` (real `.env` value left in place but unread).

### 2. Fixed — claim-invite endpoint had its own copy of the same broken check
Found while fixing #1: `server/routes/appAuth.js`'s `/claim` route (what "Link your account" calls) had its own separate inline `jwt.verify(token, SUPABASE_JWT_SECRET)`, never touched by the fix above. Would have failed every claim attempt the same way. Fixed by having it import and call the same `verifySupabaseToken`. Route handler also refactored into a named `claimHandler` export for direct unit testing.

Both bugs logged in detail in `BUGS_AND_FIXES.md` (top two entries).

### 3. New feature — self-service invite code delivery (SMS default, email option)
User has a Twilio account and wants invite codes delivered automatically instead of the admin manually generating + relaying a code. Design, confirmed with user before building:

- **Phone number is a lookup key only.** At sign-up, the user provides a South African phone number + delivery channel (SMS default, Email option). That phone number is used *only* to find the matching existing `Client` record — actual delivery always goes to `Client.contactPhone`/`Client.contactEmail` **already on file** in MongoDB, never to anything the user typed. This prevents someone who knows/guesses a real client's phone number from redirecting that client's invite code to a phone/email they control.
- **Anti-enumeration:** the endpoint always returns the same generic response (`{ ok: true, message: 'If we found a matching account, a code has been sent.' }`) whether or not a Client actually matched, so it can't be used to probe which phone numbers belong to real Mashtronics clients.
- **Rate-limited:** 5 requests/hour per IP (`express-rate-limit`, same pattern as the admin login limiter) — Twilio charges per SMS.
- **Phone matching handles messy real-world data:** existing `Client.contactPhone` values are free-text (e.g. `"+27 82 414 0291"` with spaces). Rather than an exact DB-string match (which would silently miss real records), `Client.find({archived:false})` is fetched and matched in application code via `services/clients.js`'s new `matchesPhone()`, which normalizes both sides before comparing. Fine at current client-list scale; would need a real query-level solution if the client list grows large — not done, noted as a known limitation, not a blocker now.
